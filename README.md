# WeatherStore

An Android app that fetches the current weather for any city from OpenWeatherMap, saves every reading in a local Room database, and shows the saved history as cards.

**Flow:** type a city → Retrofit calls the API → the reading is stored in Room → the list updates automatically.

## Tech stack

Kotlin · Jetpack Compose (Material 3) · Retrofit + Gson · Room (via KSP) · Coroutines & Flow · MVVM

## Project structure

```
com.example.weatherstore
├── MainActivity.kt        wires everything together
├── model/                 WeatherResponse.kt      API response shape
├── network/               WeatherApiService.kt, RetrofitInstance.kt
├── local/                 WeatherEntity.kt, WeatherDao.kt, AppDatabase.kt
├── repository/            WeatherRepository.kt    fetch + store, single data gateway
├── viewmodel/             WeatherViewModel.kt     screen state
└── ui/                    WeatherScreen.kt        Compose UI
```

## How the files connect

Each file has one job and only talks to the file next to it.

| File | Job | Talks to |
|---|---|---|
| `WeatherResponse.kt` | Describes the JSON the API sends back | Used by `WeatherApiService` and `WeatherRepository` |
| `WeatherApiService.kt` | Declares the HTTP call (`GET weather?q=city&appid=key&units=metric`) | Implemented by Retrofit, called by `WeatherRepository` |
| `RetrofitInstance.kt` | Builds the one shared Retrofit client and holds the API key | Provides `api` to `MainActivity` |
| `WeatherEntity.kt` | Describes one row of the `weather_readings` table | Used by `WeatherDao` and `WeatherRepository` |
| `WeatherDao.kt` | `insert()` a row, `getAll()` rows as a live `Flow` | Called by `WeatherRepository`, implemented by Room |
| `AppDatabase.kt` | Registers the entity and hands out the DAO | Built in `MainActivity` |
| `WeatherRepository.kt` | The only class that knows both the API and the database | Called by `WeatherViewModel` |
| `WeatherViewModel.kt` | Holds screen state, validates input, runs the fetch | Called by `WeatherScreen` |
| `WeatherScreen.kt` | Draws the state, reports taps | Talks only to the ViewModel |
| `MainActivity.kt` | Builds database → repository → ViewModel and shows the screen | Everything, once, at startup |

The screen never sees Retrofit or Room, and the ViewModel never sees the DAO. Each layer can change without breaking the ones above it.

## How the logic works

### 1. Writing: fetch and store

Tapping **Fetch** calls `viewModel.fetchWeather(city)`. The ViewModel rejects blank input, turns on the loading state, and calls `repository.fetchAndStore(city)`. The Repository then:

1. Calls `WeatherApiService`. Retrofit builds the URL, sends the request, and Gson converts the JSON into a `WeatherResponse`.
2. **Translates** that response into a `WeatherEntity` (see below).
3. Passes the entity to `WeatherDao.insert()`, and Room saves the row.

### 2. How the Repository translates the API response into the Entity

The API sends nested JSON; a Room table is flat. The Repository maps it by hand, field by field. A trimmed example of what the API returns:

```json
{ "name": "Nairobi", "weather": [{ "description": "light rain" }], "main": { "temp": 21.3, "humidity": 78 } }
```

| `WeatherEntity` field | Comes from |
|---|---|
| `id` | Generated by Room (`autoGenerate`) |
| `city` | `response.name` |
| `temperature` | `response.main.temp` |
| `humidity` | `response.main.humidity` |
| `description` | `response.weather[0].description` (the API sends a list; we use the first item) |
| `timestamp` | `System.currentTimeMillis()`, not from the API; it records when the reading was taken |

Only the fields we care about are kept; everything else in the JSON is ignored. This translation lives in the Repository so the API's shape and the database's shape can change independently.

### 3. Reading: the screen updates itself

`WeatherDao.getAll()` returns a `Flow`, which Room re-emits whenever the table changes. That list travels through `repository.getStoredReadings()` into the ViewModel, where `combine()` merges it with the loading flag and error message into one `WeatherUiState`. `WeatherScreen` watches that state with `collectAsState()` and redraws.

So the screen never displays the API response directly. It only displays what is in Room, and the insert in step 1 is what triggers the redraw. Nobody has to call "refresh".

### 4. Errors

If the fetch fails (no internet, bad key, unknown city), the ViewModel catches the exception and puts the message into the state, and the screen shows it. A `finally` block always turns the loading spinner off.

### 5. How the API key travels

`local.properties` → `build.gradle.kts` (`buildConfigField`) → generated `BuildConfig.OPEN_WEATHER_API_KEY` → `RetrofitInstance.apiKey` → used by the Repository on every request. The key is never in the source code or the Git repo.

## Setup

1. Get a free API key at [openweathermap.org](https://openweathermap.org/api). New keys can take a while to activate.
2. Add it to `local.properties` in the project root (this file is gitignored):
   ```
   OPEN_WEATHER_API_KEY=your_key_here
   ```
3. Connect a device or emulator and run:
   ```
   ./gradlew installDebug
   ```

Requirements: JDK 17, Android SDK 37 (compileSdk), minSdk 24.

## Building with GitHub Actions

Pushing to `main` builds a debug APK. Add your key under **Settings → Secrets and variables → Actions** as `OPEN_WEATHER_API_KEY`, then download the APK from the run's **Artifacts** section.

## Note

The API key is compiled into the APK through `BuildConfig`, so anyone with the APK can extract it. That is fine for a free key, but don't share builds you wouldn't want it pulled from.
